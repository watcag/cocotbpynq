# pynq-pr

Build flow, swap-aware co-simulation and PYNQ runtime **for designs generated by Cocotb-PYNQ-PR**: from one YAML file it generates the Vivado DFX design (block design, decouplers, per-partition DMA, AXI4-Stream switch, floorplan, partial bitstreams) for PYNQ-compatible boards (Zynq-7000, Kria KV260).

**Do I need this?** If you already have your own Vivado DFX design and only want to swap partial bitstreams from Python, upstream PYNQ's `Overlay.pr_download` is enough. pynq-pr is for generating DFX designs that follow its AXI4-Stream/AXI4-Lite shell, simulating module swaps with [cocotbpynq](../cocotbpynq/) before building, and loading partial bitstreams faster on the board (fpga_manager or ICAP).

## Install

Releases are published on [GitHub Releases](https://github.com/watcag/cocotbpynq/releases); replace `0.2.0` with the release you want.

On the host (the machine with Vivado and the simulator):

```bash
pip install "pynq-pr[sim]==0.2.0" verilator --find-links https://github.com/watcag/cocotbpynq/releases/expanded_assets/v0.2.0
```

The `sim` extra installs the matching cocotbpynq for `pynq-pr sim`. To run the examples, work from a clone (see the [repository README](../../README.md)).

On the PYNQ board, in the PYNQ venv, install the runtime only. It needs nothing beyond PyYAML and does not touch the image's `pynq` or `numpy`:

```bash
pip install "pynq-pr==0.2.0" --find-links https://github.com/watcag/cocotbpynq/releases/expanded_assets/v0.2.0
```

| Tool | Needed for | Version |
|---|---|---|
| Python | everything | 3.10+ |
| Vivado (+ Vitis HLS for the vision example) | `pynq-pr build` | `build.tcl` currently requires 2022.2 |
| Verilator | `pynq-pr sim` | 5.036+ (the `verilator` wheel from PyPI works; `apt` versions are too old) |
| PYNQ image on the board | running the bitstreams | v3.0.1 (PYNQ-Z1), Kria-PYNQ v3.0.1 (KV260) |

On the board, the examples' `deploy.sh` copies the bitstreams, `pynq_pr/overlay.py` (from this package) and the test script over SSH; set `BOARD_IP` and `BOARD_PSWD` (see the header of `deploy.sh`).

## Usage

Write a YAML config that describes your design:

```yaml
project: my_project
board: z1                    # z1 or kv260

sources:
  - rtl/my_module.v

reconfigurable_partitions:
  - partition_name: rp0
    modules:
      - cell_name: config_a     # name used for the output bitstream: rp0_config_a.bit
        top: my_module          # RTL module name (must match the Verilog module declaration)
        parameters:             # RTL parameter names and values (must match the Verilog parameter declarations)
          COEFFICIENTS: 5       # e.g. for: module my_module #(parameter COEFFICIENTS = 1) ...
          PIPELINE_DEPTH: 2
      - cell_name: config_b
        top: my_module
        parameters:
          COEFFICIENTS: 3
          PIPELINE_DEPTH: 4

  - partition_name: rp1
    modules:
      - cell_name: config_c
        top: my_other_module
```

All paths are relative to the working directory:

```bash
pynq-pr validate -c pr.yaml          # check config and source paths
pynq-pr build -c pr.yaml             # synth -> impl -> bitstreams
pynq-pr build -c pr.yaml --force     # overwrite existing output directory
```

Output lands in `output/<project>/bits/`: one static bitstream (`<project>.bit`), one partial bitstream per module (`<partition>_<cell_name>.bit`), plus matching `.hwh` files.

### Optional YAML fields

| Field | Default | Description |
|-------|---------|-------------|
| `reconfiguration_method` | `pcap` | `pcap` or `icap`. |
| `defines` | none | Dict of Verilog `` `define `` values applied project-wide. |

### RTL interface requirements

Your RTL modules must match these port names to connect to the shipped block design:

- AXI-Stream in: `x_TDATA`, `x_TVALID`, `x_TREADY`, `x_TLAST`
- AXI-Stream out: `y_TDATA`, `y_TVALID`, `y_TREADY`, `y_TLAST`
- AXI-Lite slave: `s_axi_AXILiteS_*`
- Clock: `clk`, Reset: `rst_n`

## Supported Boards

| Board | Part | FPGA |
|-------|------|------|
| z1 | xc7z020clg400-1 | Zynq-7000 |
| kv260 | xck26-sfvc784-2LV-c | Kria KV260 |

The PYNQ-Z2 uses the same device as the Z1 but is untested. PYNQ v4.0 no longer supports the Z1/Z2, so use a PYNQ v3.x image on those boards.

## Reconfiguration Methods

- **pcap** (default): the PS reconfigures the FPGA over PCAP. Standard PYNQ flow.
- **icap**: the FPGA reconfigures itself over ICAP using the Versatile DPR infrastructure. No PS involvement at reconfiguration time.

The bundled examples use `icap`. On the KV260, ICAP requires the custom PMU firmware described in [docs/kv260](../../docs/pynq-pr/kv260/README.md); without it, set `reconfiguration_method: pcap` in the example YAML.

## Examples

- **[Add/Sub](../../examples/pynq-pr/add_sub/)**: three independent reconfigurable partitions, each with polynomial module variants.
- **[Vision](../../examples/pynq-pr/vision/)**: two reconfigurable image filter partitions chained through an AXI-Stream switch, with four HLS-generated 3×3 kernels.
- **[Attention](../../examples/pynq-pr/attention/)**: scaled dot-product attention computed by sequentially reconfiguring a single partition through QK matmul, softmax, and PV matmul stages.

## Simulation

`pynq-pr sim` runs the same Python test used on the board against the RTL, swapping reconfigurable modules as separate processes (no Vivado needed). It exits non-zero if a test fails. For example:

```bash
cd examples/pynq-pr/add_sub
pynq-pr sim -c pr_z1.yaml --test pr_test.py -f   # -f: regenerate sim/ if it exists
```
